# AI 原生业务工作台

**一款轻量、可扩展的 AI 原生业务工作平台。**

简体中文 · [English](./README.md) · [开发路线图](./ROADMAP.md)

> **公开开发中：** 本仓库从项目初始化开始持续公开更新。当前以「完整工作台 + 通用微内核 + 软件研发内置插件」作为首个产品基线。功能将随代码与版本逐步落地；文中的产品能力与长期规划不代表当前版本已经全部实现。

> **让 AI 处理业务细节，让人类掌握业务全局。**

## 为什么需要这样的工作台？

AI Agent 已经能够参与编程、资料分析、内容创作和越来越复杂的业务任务。但当实际工作越来越多地交给 AI，人类反而可能越来越难回答几个基本问题：

- 这项工作究竟发生了什么变化？为什么会发生？
- 哪些结果已经验证，哪些只是 AI 的判断，还有哪些风险没有解决？
- 已经确认的决策、规则和经验，能否在下一次 Agent 会话中继续发挥作用？
- Agent 能否按需获取相关背景，而不必重复阅读大量历史对话和文档？
- 用户能否不专门学习上下文工程、提示词工程、Skill 工程或复杂管理方法，也能使用这些基础设施？

**AI 原生业务工作台（AI-Native Business Workbench）** 围绕这些问题设计。它将人类能够理解的业务工作台，与 AI 可以结构化访问和复用的业务知识连接起来，帮助减少重复管理、上下文恢复及信息整理成本，同时保持工作过程可理解、结果可追溯、重要决策可由人类掌握。

它不以替代现有 Agent Harness 或接管执行调度为目标，也不要求用户把所有工作迁移到新的流程中。它更关注：**让人和 AI 都能理解、积累并治理已经开展的业务工作。**

## 产品组成

系统采用**工作台 + 通用微内核 + 业务插件**的架构：

| 层次 | 职责 |
| --- | --- |
| **统一工作台** | 通过 Electron 桌面端和 Web 界面，为人类提供简洁、渐进式的业务视图和操作入口。 |
| **通用微内核** | 由独立运行的 Go 服务提供工作区、数据、对象关系、事件、权限、证据、AI 能力和插件生命周期等基础设施。 |
| **业务插件** | 按领域定义业务对象、专业流程、规则、工具、集成和专属界面，可按需安装或启用。 |

**「软件研发工作台」是第一款内置业务插件，也是首版产品的业务基线。** 未来可逐步支持游戏、内容创作、汽车、制造业、半导体、金融等其他业务领域。不同领域共享可靠的底层能力，同时保留自己的工作方式，不必套用软件研发流程。

## 我们想提供的体验

### 1. 即使工作大部分交给 AI，人类仍能看懂全局

打开工作台，首先看到当前状态、重要变化、可核查证据、待解决风险和需要自己决定的事项。只有想了解更多时，才展开日志、关系和专业细节。

### 2. 知识持续积累，Agent 按需取用

将决策、约束、关联和经验组织成可复用、可追溯的信息，让 Agent 在执行任务时优先获取有关上下文，减少重复探索。是否真正节省 Token、时间和综合成本，将通过真实任务验证，并计入系统自身的维护与模型开销。

### 3. AI 辅助治理，而不是增加管理工作

AI 可以辅助整理变更、发现关系、提炼知识、核对证据、提出风险和决策建议。系统明确区分可核查的事实、AI 的解释和未经证实的主张；涉及关键授权和受保护的工程或业务资料时，由具备权限的人类作出决定。

### 4. 上手简单，能力上限足够高

基础功能尽可能开箱即用，无须配置复杂的 Agent 工作流。专业用户可以进一步查看证据、调整规则、使用 API，或安装所属行业的业务插件。

### 5. 本地优先，多入口访问

Go 后端能够独立运行并托管 Web 界面。Electron 是可选的桌面视图，不是系统运行的前提。系统优先面向 Windows 和 Linux 的本地工作区，同时考虑跨平台可移植性。

## 首款内置插件：软件研发工作台

软件研发插件面向由人类与 AI Agent 共同参与的软件项目，主要提供以下业务能力：

- **项目概览：** 查看项目现状、近期变化、待解决问题及需要人类介入的事项。
- **工程资产与追溯：** 关联需求、设计、代码、测试、文档、变更和验证证据。
- **工程知识与记忆：** 分别管理近期工程事实、中期待办与待裁决事项、经过人类确认的长期知识。
- **工程规范：** 维护规则、约束和开发指南，并在适用场景下提供 `AGENTS.md` 的可视化管理。
- **变更与证据审查：** 关联 Git 变更、测试结果、影响分析、技术主张及审查记录。
- **人类治理：** 让重要决策、风险、审批和裁决依据清晰可见。
- **AI 辅助理解：** 基于可核查的工程来源，生成摘要、解释和建议。

这部分能力继承了我们对 **EG（Engineering Governance，工程治理）** 的研究。EG 作为软件研发领域的治理方法和能力继续演进；通用微内核本身不绑定软件工程语义。

## 系统如何工作？

![AI 原生业务工作台的概念架构](./docs/public/architecture-overview.svg)

```text
                    面向人类的工作台
            ┌─────────────┬─────────────┐
            │ Electron 桌面│   Web 浏览器 │
            └──────┬──────┴──────┬──────┘
                   └──────┬──────┘
                          │ 统一服务接口
                   ┌──────▼──────┐
                   │  Go 通用微内核 │
                   │  可独立运行   │
                   └───┬─────┬───┘
                       │     │
              ┌────────▼┐  ┌─▼─────────────┐
              │ 本地工作区 │  │ 领域业务插件   │
              │ 数据与证据 │  │ 软件研发等     │
              └─────────┘  └───────────────┘
                          ▲
                      授权接口
                          │
              Agent / CLI / MCP / Harness 适配器
```

人类工作台和 Agent 接入端访问同一套受治理的数据。**业务插件用于扩展“能处理什么业务”，Harness 适配器用于扩展“谁能接入使用”**，两者相互独立。

## 三种运行形态

| 形态 | 使用方式 |
| --- | --- |
| **Desktop 桌面模式** | 通过 Electron 客户端管理本地项目，获得原生桌面交互体验。 |
| **Web 浏览器模式** | 仅运行 Go 后端，通过浏览器访问管理界面，无须启动 Electron。 |
| **Headless 无界面模式** | 只运行 Go 服务，通过 API 或自动化接口使用系统能力。 |

前端采用 **React + TypeScript**，在桌面端与 Web 端复用。后端采用 **Go**，使用 **SQLite 与工作区本地文件**保存数据；构建后的 Web 资源可由 Go 程序直接提供。

## AI 与外部生态

系统计划通过统一接口提供治理与业务能力，包括 **MCP、Agent Skill、CLI/HTTP API**，以及面向 **DeepSeekHarness（DSH）、Codex** 等环境的接入适配器。

外部接入适配器通过经过授权的公共接口使用核心服务，不重复实现治理内核，也不能绕过受保护的数据和规则。

内置 AI 治理助手只负责辅助理解、整理、分析与建议，不接管宿主 Harness 的模型调度、多 Agent 团队或任务运行时。

## 产品原则

1. **人类理解优先。** 让用户看懂结果，不要求先成为 AI 工程或项目管理专家。
2. **信息一次沉淀，按需复用。** 减少重复文档、重复上下文和多份权威来源。
3. **事实可验证，结论可追溯。** 明确证据、假设与 AI 推断的区别。
4. **关键决策由人类掌握。** 权限边界、审批与裁决清晰可控。
5. **本地优先，尊重既有项目。** 不因接入工作台而强制迁移或重写历史资料。
6. **小内核，宽领域。** 专业业务流程由插件扩展，内核保持通用和稳定。
7. **渐进式复杂度。** 普通用户开箱即用，专业用户可以深入配置与扩展。
8. **评价实际净收益。** 除了 Token 节省，也衡量分析、索引、模型调用和人工审查成本。

## 项目发展方向

首版产品以**完整可用的桌面/Web 工作台、独立 Go 微内核、本地数据体系、可选 AI 辅助治理能力，以及「软件研发工作台」内置插件**作为基线。统一扩展契约从首期设计开始考虑，其他行业插件和 Harness 接入适配器可以在后续阶段逐步增加。

项目正围绕上述架构推进开发。本文介绍的是产品设计和发展方向，并不意味着所有规划能力均已发布。
